# Orbiter — Project Plan

A modern riff on the early-2000s gravity slingshot web game. You set **launch direction, power,
and timing**, then let gravity do the rest. The game is 2D on a single plane, but every planet,
star, and ship is a full 3D object with particles and weather. You can drop into a **3D chase cam**
at any time during flight.

## Design pillars

1. **One shot, many forces.** Your only direct input is the launch. Mastery comes from reading gravity wells,
   space weather, and moving bodies.
2. **Readable but not fully predictable.** The aim preview shows *static gravity only*. Solar wind gusts,
   flares/CMEs, and moving moons are *not* in the preview, so you have to learn their timing.
   Turning the preview off is an optional hard mode.
3. **Beautiful chaos.** Planets have living surfaces, clouds, storms, auroras, embers, and coronas.
   The 3D fly-through should feel like riding the trajectory.
4. **Runs that build (roguelite + KSP).** Between levels you pick upgrades and ship parts. Mass, sensors,
   shields, and boosters change how you can play the next sector.

## Tech decisions

| Area | Choice | Why |
|---|---|---|
| Engine | Godot 4.7, GDScript, Forward+ | Free, light, great 3D particles and shaders, text-based scenes that diff well for two people |
| Physics | Godot `RigidBody3D` (Jolt), custom gravity in `_integrate_forces` | Chosen for an organic, slightly unpredictable feel. Movement is locked to the Z=0 plane |
| Aim preview | Separate integrator that only uses static gravity | Honest estimate; preview length is an upgradable stat |
| Planets | Procedural shaders in Godot, driven by a `PlanetType` resource | Endless variety from parameters; no texture painting needed |
| Ship / portal / props | Generated by Python scripts in Blender, exported as `.glb` | Repeatable: edit the script, rebuild, re-import |
| Collaboration | GitHub `matthewaharris/orbiter` (private), feature branches + PRs | |

## Roadmap

### Phase 0: Setup ✅
Install Godot, Blender, and the MCP servers. Create the repo and project skeleton.

### Phase 1: Vertical slice demo (current)
- Slingshot aiming: drag with the mouse, fine-tune with the keyboard, launch.
- Gravity from planets and stars on a `RigidBody3D` ship.
- Aim preview arc (P toggles it, length set by the ship's sensor stat).
- Portal goal; crash, out-of-bounds, and timeout handling; instant retry.
- Tactical camera ↔ 3D chase cam toggle (C).
- 5 handcrafted levels:
  1. *First Arc*: one rocky planet.
  2. *Twin Pull*: two planets.
  3. *Solar Weather*: a star with solar wind and periodic CMEs, so launch timing matters.
  4. *Moon Window*: a gas giant with an orbiting moon that blocks or assists.
  5. *The Gauntlet*: lava world, ice world, star, and moon.
- Visuals: procedural planet shader, cloud/weather layer, atmosphere rim, star corona, starfield and nebula sky, bloom,
  ship engine trail, portal swirl, crash explosion, win burst.

### Phase 2: Roguelite run loop
- A run is a sector map of procedurally assembled levels from the world scheme (`docs/WORLD_SCHEME.md`).
- Pick 1 of 3 upgrades after each clear: boost charge, black hole deployer, longer preview, CME shield, mass reducer.
- Hull integrity: hazards damage you instead of instantly killing you. The run ends at 0.
- Meta progression: unlock parts between runs.

### Phase 3: Ship builder (KSP flavor)
- Modular ship: hull + engine + sensor + utility slots. Each part has mass, a stat, and an art piece (Blender).
- Mass vs. launch power trade-off. Heavier ships launch slower but resist solar wind.
- Assemble and preview in a 3D hangar scene.

### Phase 4: Content and polish
- More planet and star archetypes, music/SFX, juice, controller support, level editor (son-friendly!), and a Steam/itch build.

## Working with Claude (calibration notes)
- Claude can write all the code, shaders, and Blender scripts, run Godot headless to catch script errors,
  and capture screenshots to check visuals.
- Claude **can't feel** the game. Tuning sessions should be: you play → describe what feels off → Claude adjusts numbers.
- Tunable numbers are kept in exported properties and `game/scripts/tuning.gd` so they're easy to tweak in the editor.
